# Building and running

The app is an Expo development-build project: native modules (and later Vapi and a widget target) rule out Expo Go. `ios/` and `android/` are generated by `expo prebuild` and are not committed.

The app is called Juno. `expo.name` in app.json sets the home-screen label, the name in iOS alerts and permission prompts, and the Xcode project and product (`Juno.xcworkspace`, `Juno.app`); in code the name comes from `APP_NAME` in `src/appName.ts`. Some identifiers keep the old name on purpose:

| Identifier | Value | Why it stays |
| --- | --- | --- |
| Bundle identifier and Android package | `com.akhileshrangani.consumerhack` | Changing it makes iOS treat the app as a different one, which loses its keychain sign-in. |
| `expo.slug`, package.json `name` | `consumerhack` | Not shown to users. |
| URL schemes | `juno`, then `consumerhack` | `juno://` is the main scheme. `consumerhack://` stays registered so older links and instructions keep working. |
| Revyl app label | `consumerhack` | Only names the build history in `tools.mobile.build`. |
| Supermemory container prefix | `consumerhack_` (`convex/memory.ts`) | Renaming it would orphan every stored memory. |

The OAuth redirect scheme doesn't come from app.json. It is the reversed Convex site host (`site.convex.dependable-goshawk-583`), so the rename doesn't touch it.

## Local checks

```bash
pnpm install
pnpm lint
pnpm typecheck
pnpm test
pnpm exec expo export --platform ios --platform android --platform web   # bundles all platforms
pnpm web                                                                 # run in a browser
```

## Binaries

Two scripts produce Release binaries with the JavaScript bundle embedded, so they run without a Metro server:

| Script | Output |
| --- | --- |
| `scripts/build-ios-simulator.sh` (needs macOS and Xcode) | `ios/build/Build/Products/Release-iphonesimulator/Juno.app` |
| `scripts/build-android-apk.sh` (needs JDK 17+ and the Android SDK) | `android/app/build/outputs/apk/release/app-release.apk` |

`EXPO_PUBLIC_*` variables are inlined at build time, so set them in the build environment.

`patches/expo-dev-launcher@58.0.20.patch` removes a call to `axisBehavior`, an iOS 27.1 toolbar API that Xcode 27.0 (Revyl's runner) does not have. Drop the patch when expo-dev-launcher is upgraded past 58.0.20 with a fix, or when the iOS runner moves to Xcode 27.1 or later; pnpm refuses to install if the patched version changes, so an upgrade forces the decision.

### On Revyl from a Capy thread

Capy machines have no Xcode or Android SDK. Build on Revyl's runners with `tools.mobile.build`, with the repository directory as the workspace source and one of the scripts as the only command:

```js
await tools.mobile.build({
  action: 'start',
  platform: 'ios', // or 'android'
  app: 'consumerhack', // Revyl's label for the build history only; kept so earlier builds stay in one list
  source: {
    type: 'workspace',
    path: 'consumerhack',
    commands: ['bash scripts/build-ios-simulator.sh'], // or scripts/build-android-apk.sh
    output_path: 'ios/build/Build/Products/Release-iphonesimulator/Juno.app', // or the APK path above
  },
});
```

Then `tools.capy.phone` with `attach` and `install` puts the build on a cloud phone. `.capyignore` keeps local env files out of the upload.

### Build settings for Revyl

`EXPO_PUBLIC_*` values are inlined when the bundle is built, so a Revyl build needs them on the runner. `scripts/build-ios-simulator.sh` loads an optional `build.env` file from the repository root (gitignored, but uploaded with the workspace because `.capyignore` does not exclude it). Write it right before starting the build:

```bash
printf 'EXPO_PUBLIC_VAPI_PUBLIC_KEY=%s\nEXPO_PUBLIC_CONVEX_URL=https://dependable-goshawk-583.convex.cloud\nEXPO_PUBLIC_DEV_AGENT_LINK=1\n' "$VAPI_PUBLIC_KEY" > build.env
```

Only public values go in it: the Vapi public key is meant to ship in the app. Leave out `EXPO_PUBLIC_DEV_AGENT_LINK` for anything other than a test build.

### Waking the agent without a circle (test builds only)

Cloud phones cannot draw a circle. In a build made with `EXPO_PUBLIC_DEV_AGENT_LINK=1`, opening the link `juno://dev-agent` (or the older `consumerhack://dev-agent`, which still works) wakes the voice agent exactly as a clockwise circle does (handled in `src/app/+native-intent.tsx` and `src/agent/devWake.ts`). If the feed is not showing yet, the agent wakes as soon as it is. In a build without the variable the check is the constant `false`, the bundler removes the code, and the link just opens the app. On a simulator: `xcrun simctl openurl booted juno://dev-agent`.

The same test builds print the call's lifecycle to the device log as `[agent] ...` lines (connecting, connected, each tool name, ended reason, exit). They never include what was said or any post text.

### Reading the agent's log on a physical iPhone

The lines that show whether the publish checks misfire on a real call:

| Line | Meaning |
| --- | --- |
| `[agent] assistant speech during read-back {"speaker":"app","by":"source","source":"force-say","turn":3}` | Assistant speech arrived while a read-back waited for its yes, and was put down to the app's own words. `source` and `turn` are exactly what Vapi sent in `assistant.speechStarted` (`null` when it sent nothing). `by` is `source` when Vapi's named source decided it, or `timing and words` when Vapi named none and the app had to rely on a due `say()` plus the words being the read-back. Many `timing and words` lines mean Vapi's source events aren't arriving. |
| `[agent] assistant speech during read-back {"speaker":"model",...}` then `[agent] yes voided by assistant speech {...}` | The speech was put down to the model, so the next yes doesn't count and the draft is read back again. When in doubt the app puts speech down to the model, so if this follows every read-back, look at `source` and `turn` to see what Vapi sends. |
| `[agent] publish refused {"reason":"..."}` | `publish_draft` was refused: `expired` (the yes wasn't the very next answer), `wrongVerb` ("delete it" for a post), `notAffirmative`, `sameTurn`, `notReadBack`, `staleDraft`, `noDraft` or `alreadyPending`. |
| `[agent] publish confirmed`, `[agent] held from transcript`, `[agent] undone from transcript` | A yes was accepted; something other than a yes during the five seconds held the send; an undo stopped it. |

How to see them:

- **Development build (`eas build --profile development`) with Metro running:** the lines appear in the terminal running `npx expo start`.
- **Any build made with `EXPO_PUBLIC_DEV_AGENT_LINK=1`, without Metro:** the lines go to the iPhone's system log as errors. On a Mac, connect the iPhone, open the Console app, select the iPhone in the sidebar, press Start, and type `[agent]` in the search field. From a terminal, with libimobiledevice installed: `idevicesyslog | grep '\[agent\]'`.
- **Simulator:** `xcrun simctl spawn booted log stream --predicate 'eventMessage CONTAINS "[agent]"'`.

Release builds without the variable print these lines with `console.log`, which iOS doesn't keep, so use a build with the variable for the first real calls.

`eas.json` has `development` (dev client), `preview` and `production` profiles: `npx eas-cli build --profile development --platform ios`. This needs an Expo account and, for iOS, an Apple developer account.

## Convex

`pnpm convex:dev` creates or links a personal deployment, pushes `convex/`, regenerates `convex/_generated` and writes `EXPO_PUBLIC_CONVEX_URL` to `.env.local`. With `CONVEX_DEPLOY_KEY` in the environment, `npx convex deploy` pushes to the deployment the key belongs to.

The app talks to the deployment at **https://dependable-goshawk-583.convex.cloud** (not a secret). `scripts/build-ios-simulator.sh` sets it as `EXPO_PUBLIC_CONVEX_URL` unless the environment already sets one, so Revyl builds get post descriptions and memory. The app still runs without it: narration then has no picture descriptions, and the voice agent works without memory.

Server-side keys live only in the deployment's environment. Set them without echoing the value:

```bash
npx convex env set SUPERMEMORY_API_KEY "$SUPERMEMORY_API_KEY"   # convex/memory.ts
npx convex env set OPENAI_API_KEY "$OPENAI_API_KEY"             # convex/describe.ts, picture descriptions
npx convex env set DESCRIBE_MODEL gpt-6-luna                    # optional, this is the default
```

| Variable | Where it is set | Read by |
| --- | --- | --- |
| `SUPERMEMORY_API_KEY` | Convex deployment only | `convex/memory.ts` |
| `VAPI_PRIVATE_KEY` | developer shell only | `pnpm eval:agent` (Vapi chat API) |
| `OPENAI_API_KEY` | Convex deployment, and developer shell | `convex/describe.ts` (picture descriptions); `EVAL_BACKEND=openai pnpm eval:agent` (stand-in) |
| `DESCRIBE_MODEL` | Convex deployment only, optional | `convex/describe.ts` (defaults to `gpt-6-luna`) |
| `BLUESKY_TEST_HANDLE`, `BLUESKY_TEST_APP_PASSWORD` | developer shell only | `pnpm eval:bluesky` |

None of these is ever set in the app or in `.env.local`. The voice agent's Convex code reads only `SUPERMEMORY_API_KEY`. The only deployed code that calls a model is `describe:describePost`, which takes a post URI, fetches the post from Bluesky itself, and is capped at $2 of model spend an hour (see [narration.md](narration.md)).

### Who can use a memory

- **Signed out**, memory is keyed by a random id that never leaves the phone, with a secret in the keychain. The first device to use the id owns it.
- **Signed in**, memory is keyed by the Bluesky DID, which is public, so every call proves the account (`convex/memoryAuth.ts`, AKH-18). The phone asks its own Bluesky server for a service-auth token through `com.atproto.server.getServiceAuth`. The token is for this deployment (`did:web:<deployment>.convex.site#juno_memory`) and for Juno's memory method only (`com.akhileshrangani.juno.accessMemory`), and it lasts 60 seconds.
- **How Convex checks a token.** Convex checks the signature against the `#atproto` key in the account's DID document, and accepts each token once. A token opens a session for a random secret made on the phone, so the rest of that minute's calls need no new token. Any phone signed in as the account reads the same memory.
- **What never reaches Convex, Vapi or Supermemory:** the Bluesky session itself, meaning access and refresh tokens, DPoP keys and app passwords.
- **What a captured token allows.** Someone who captures a token and gets it to Convex before the phone does can read, add to and forget that person's memory until the token expires, at most 60 seconds, and nothing else. It opens nothing on Bluesky or any other service. Once used, it is refused. A captured session secret gives the same access for the same time.
- **OAuth sign-ins** need the scope `rpc:com.akhileshrangani.juno.accessMemory?aud=did:web:<deployment>.convex.site%23juno_memory`. The client metadata pins it to the deployment that serves the metadata, so the grant can't mint memory proofs for any other service. If the client id moves elsewhere (AKH-24), the scope must still name the memory deployment.
- **People who signed in with OAuth before the scope was added** have to sign in again before memory works. Their server refuses the proof with 403 "Missing required scope". The first time memory comes up in a conversation, the agent says in one sentence that remembering needs them to sign in again, and offers to open sign-in. After that it doesn't repeat it. Everything else works. App-password sessions need nothing new.
- **DID documents** come only from plc.directory (`did:plc`) or from a public host name (`did:web`, with no port and no path). A `did:web` host is fetched from a Node action (`convex/didWeb.ts`). That action connects only to the addresses it checked and refuses private, loopback, link-local and similar ranges. Neither fetch follows redirects, and both stop after 3 seconds or 64 KB, counted as the body streams in.
- **Fetches are cached and limited**, so garbage proofs can't switch memory off for everyone. A proof is fully checked before any fetch: its structure, account, audience, method and lifetime, and that the account is a `did:plc` or a safe `did:web`. A key that verified is cached for 24 hours, so a returning user costs no fetch. A key the account rotated away can keep opening that account's memory, and nothing else, for up to a day. After any fetch of a DID, whether it found a key, found none, or the proof then failed, that DID isn't fetched again for 10 minutes, which also bounds key-rotation refetches. A fetch that fails or finds no key keeps the key verified before, which stays in use until a fetch returns a different one: anyone can force a refetch with a badly signed proof, and while plc.directory is failing that would otherwise lock the account's owner out. The OAuth scope's memory audience, the proof the app asks for and the audience the deployment accepts must agree; `src/agent/__tests__/memoryAudience.test.ts` fails if the client id (AKH-24) or the build's Convex URL moves without the others.
- **Fetch windows.** Each caller address may cause 6 fetches an hour, and the deployment 300. A fetch is needed only the first time an account is seen in a day, so 300 an hour covers about 7,200 different accounts a day, far beyond Juno's use, while one address can take at most 2% of it.
- **Known limit, unchanged:** two addresses calling at their full memory rate (60 per 10 minutes each) can still use up the deployment's 600 memory calls an hour.
- **Checking against the real servers.** `pnpm eval:memory-proof` runs the checks with the test account in `BLUESKY_TEST_HANDLE` and `BLUESKY_TEST_APP_PASSWORD`.
- **After the first deploy of this change**, run `npx convex run memoryAccess:clearAccountClaims`. It deletes any device-secret claim left on a `bsky:` key. Those claims are no longer read, so this is cleanup only.

When someone saved memories while signed out and then signs in, the agent's first words ask whether to keep them with their account (`src/agent/memoryOffer.ts`). They move only on a plain yes in the person's very next turn, the same rule as a publish confirmation. Any other turn closes the question. They can ask for it again by name ("keep what I saved before signing in"), and the app then asks it again. On a no the memories stay on the phone, and that account isn't asked at the start again.

The memory actions are rate limited per user (30 calls per 10 minutes), per caller address (60 per 10 minutes, stored as a hash) and for the whole deployment (600 per hour). DID document fetches have their own limits (above), and a person can keep at most 50 facts. The numbers live in `src/agent/memoryRateLimits.ts`. The caller and deployment limits are taken before any proof is checked or document fetched. The user limit is taken only after the secret or the proof checks out, so a stranger who knows someone's DID can't use up their allowance. Known limit: whoever uses up the whole-deployment allowance turns memory off for everyone until the hour is over. The voice agent still works then, without memory.

Deploy only from main: a deploy replaces every function on the deployment, and main is the only place where every Convex change lives together. After every deploy, run the metadata check below. The branch `capy/convex-union-deploy` was a temporary union of open pull requests used before they merged; it is retired. Never deploy from it.

### Bluesky OAuth client metadata

Bluesky sign-in needs Juno's OAuth client metadata at a public https URL, and that URL is the client id. A Convex HTTP action serves it (`convex/oauth.ts`, route in `convex/http.ts`, document built by `convex/oauthClientMetadata.ts`, which the app imports too, so the two can't drift):

```
https://dependable-goshawk-583.convex.site/oauth/client-metadata.json
```

The native redirect URI is the reverse of that host, `site.convex.dependable-goshawk-583:/oauth/callback`, as the AT Protocol requires. The iOS system sign-in sheet catches it, so it needs no entry in app.json. Every deploy of `convex/` must include these files, or Bluesky refuses every sign-in with `invalid_client_metadata`. Check after deploying:

```bash
curl -sD - https://dependable-goshawk-583.convex.site/oauth/client-metadata.json
```

The response must be 200 with `content-type: application/json`, and its `client_id` must equal the URL. To point a build at another deployment, set `EXPO_PUBLIC_BLUESKY_OAUTH_ORIGIN` to its `.convex.site` origin at build time.

The scopes in `OAUTH_SCOPES` are the least the provider needs: create and delete on posts, likes and reposts, `image/*` blobs, and signed-in reads of the timeline, an author feed, posts, a post thread and a profile, all addressed to the Bluesky AppView. Bluesky's server refuses any call under an OAuth session that no granted scope covers. `src/social/bluesky/__tests__/oauthScopes.test.ts` runs every `SocialProvider` method under an OAuth session and fails when one of them makes a call without a granted scope. Its table is typed by the interface, so a new method doesn't compile until it's added there. Changing the scopes changes the metadata, so deploy Convex after such a change and check the URL again. Users who signed in earlier keep their old grant until they sign in again.

## Testing the voice agent without a microphone

`pnpm eval:agent` runs `src/agent/__eval__/vapiChat.eval.ts` on a developer machine: it sends a scripted conversation to the real assistant configuration through Vapi's chat API with `VAPI_PRIVATE_KEY` from your shell, runs every tool call through the real tool handlers against a mocked Bluesky account, and writes the transcript to `agent-eval-transcript.md` (or `EVAL_TRANSCRIPT`). Vapi's chat API needs a card on the Vapi account and is billed. With `EVAL_BACKEND=openai` and `OPENAI_API_KEY` it sends the same prompt and tools to the same model at OpenAI instead: a stand-in that tests the prompt and tools but not Vapi's own orchestration.

Each step of the script says what correct looks like, and the transcript opens with a pass or fail per step. The safety steps are the ones where publishing would be wrong: a hedge after a read-back, a yes with a change attached, "yes, delete it" on a post, a yes to the agent's own question, and a change during the five seconds. These check that the model held back, not only that the app's guard caught it. The last three steps are harder requests: two actions in one sentence, "send that to Maya" (no tool fits, so the agent should ask or explain rather than guess), and a correction in the middle of dictation. The stand-in streams, so it also records each turn's time to the first token, its total time and its cost. `EVAL_RESULTS=<file>` writes those as JSON.

## The voice agent's model

The model is `AGENT_MODEL` in `src/agent/assistant.ts`: gpt-5.6-sol, the most capable model Vapi offers, with reasoning off (`reasoningEffort: 'none'`), OpenAI's fast tier (`serviceTier: 'fast'`) and temperature 0.2. It replaced gpt-4.1 in AKH-42, after Akhilesh found the agent too dumb at times. In the eval it matched or beat gpt-4.1 on every task and safety step. It starts each answer about 0.2 seconds later and costs about 60% more per turn; the fast tier keeps that gap small. The comparison is in that pull request. To compare models, override the shipped one:

```sh
EVAL_BACKEND=openai EVAL_MODEL=gpt-5.6-sol EVAL_REASONING_EFFORT=none EVAL_SERVICE_TIER=fast pnpm eval:agent
EVAL_BACKEND=openai EVAL_MODEL=gpt-4.1 EVAL_REASONING_EFFORT= pnpm eval:agent   # a model without reasoning
```

Things that constrain the choice:
- Take model ids from Vapi's list (docs.vapi.ai/providers/model/openai), not OpenAI's. Some OpenAI models, such as gpt-6.1-sol, aren't offered through Vapi.
- On the GPT-5.x and GPT-6 models, OpenAI accepts a temperature other than 1 only with reasoning off, which is why `reasoningEffort: 'none'` sits beside the model. Remove it, and `serviceTier`, if you switch to a model without reasoning, such as gpt-4.1. With function tools on Chat Completions, gpt-6-luna refuses any reasoning effort above `none`.
- Vapi refuses `reasoningEffort: 'none'` for gpt-5.5.
- Reasoning at `low` added about 0.3 to 0.75 seconds per request in AKH-42's measurements.
- Vapi's fast service tier (`serviceTier: 'fast'`) costs twice as much per token. It applies only to gpt-6-luna, gpt-5.6-sol, gpt-5.6-terra, gpt-5.6-luna and gpt-5.5, and Vapi ignores it for other models.
- After a hedge ("okay let me think"), the GPT-5.6 models kept asking what to change, even after "go ahead", until the publishing rules said to call publish_draft anyway on a later yes. The app reads the draft again first, so this never posts without a fresh yes.

Before shipping a new model, confirm Vapi accepts the configuration by creating and then deleting a test assistant through Vapi's API, with `VAPI_PRIVATE_KEY` from your shell.

### Billing the model to your own OpenAI account

Vapi can call OpenAI with your own API key. Add it in the Vapi dashboard under Integrations. Vapi then stops charging for the model, and OpenAI bills your account directly at its own prices. Some models may only be available through Vapi once a provider key is added. The key is entered only in Vapi's dashboard: it never goes into the app, `build.env`, `.env`, or this repository, and the app never sees it. Akhilesh added his OpenAI key there on 2026-11-15, so the agent's model is billed to his OpenAI account.

`pnpm eval:bluesky` publishes a real post and reply through the tool handlers to the account in `BLUESKY_TEST_HANDLE`/`BLUESKY_TEST_APP_PASSWORD`, undoes and deletes them, and checks each step on Bluesky. Use a throwaway account.
